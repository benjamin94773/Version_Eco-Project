1. Arquitectura del Software Bajo Prueba (SUT)

Contexto Técnico

Capa 1: Frontend SPA

React 18 + Vite en localhost:5173.

  • Validación nativa HTML5 (min, required).
  • Diálogos nativos (alert, confirm).
  • Semáforo de alertas en Dashboard.

Capa 2: Backend API

Node.js 24 + Express 4 en localhost:4000/api.

  • Endpoints REST JSON semánticos.
  • Códigos 200, 201, 400, 409, 500.
  • Generador de recetas PDFKit.

Capa 3: Base de Datos

PostgreSQL 18 (version_eco_db).

  • Procedimientos PL/pgSQL atómicos.
  • Restricciones CHECK e índice LOWER(TRIM).
  • Vistas reactivas de stock mínimo.

Cadena de Valor Funcional Evaluada (4 Funcionalidades No-CRUD)

Unicidad, tope 50 (RN-04), historial, no borrar si hay receta.
F2: Fórmulas (BOM)
Mínimo 1 insumo (RN-08), sin repetidos (RN-14), cantidad > 0.
F3: Producción Central
Descuento atómico PL/pgSQL (RN-10), rollback y alertas.
F4: Traslados a Sedes
Solo desde Central, control de límite stock, suma acumulativa.

2. Actualización del Plan Maestro de Pruebas (PMP)

Estrategia de Automatización

Se integró la Estrategia de Automatización Funcional E2E Multicapa dentro de la Sección 7.4 del Plan de Pruebas para asegurar regresión determinística:

1. Validación Multicapa Real (Sin Mocks)

  • Interfaz: Acciones reales de usuario en Chrome sobre React.
  • Red HTTP: Interceptación con waitForResponse() para validar el código de estado devuelto por Express.
  • Base de Datos: Consulta directa a PostgreSQL (getStocksSnapshot()) tras cada operación para certificar persistencia ACID.

2. Aislamiento Determinístico (Sandboxing)

  • Reto del $L_9$: Producción consume stock y traslados dependen de Central.
  • Solución: Antes de cada test, resetBaseline() ejecuta TRUNCATE ... RESTART IDENTITY CASCADE y siembra las precondiciones exactas en ~20 ms.
  • Orden controlado: workers: 1 evita colisiones sobre la BD.

3. Sincronización Reactiva

Cero esperas fijas (no sleep). Auto-waiting nativo de selectores, checkValidity() para bloqueos HTML5 y waitForEvent('dialog') para alertas React.

4. Gestión Automática de Evidencias

Captura automática de pantallazos PNG, contexto DOM y trazas interactivas (trace.zip) ante cualquier falla, consolidadas en Reporte HTML y JSON.

4. ¿Por qué Playwright + Driver pg? (Socialización)

Decisión Técnica

Ventajas Clave Frente a Competidores

  • Vs. Postman/Newman: Postman no abre navegador; no podría probar bloqueos HTML5 (F3-CP-10..12) ni alertas visuales en el Dashboard.
  • Vs. Selenium: Sin gestión manual de drivers ni sleep() frágiles; Playwright trae auto-waiting y reporte HTML nativo.
  • Vs. Cypress: Manejo nativo limpio de window.alert() (necesario en F2 Fórmulas), validación directa de checkValidity() y menor consumo en Windows.
  • Vs. Katalon: 100% Open Source y escrito en JavaScript ESM (mismo lenguaje del equipo), sin licencias ni Groovy externo.

7. Hallazgos Relevantes y Defectos Descubiertos

Evidencia de Calidad

DEF-02 (Nuevo): Tope de 50 kg no validado — F1-CP-05

Regla violada: RN-04 (máximo 50 unidades).

Al ingresar 50.01 para Glicerina, ni el formulario ni el endpoint bloquean el valor. Playwright capturó Expected >= 400, Received 201 y persistió 50.01 en BD.

DEF-03 (Nuevo): Permite fórmulas vacías — F2-CP-02

Regla violada: RN-08 (mínimo 1 materia prima).

Al guardar una fórmula con detalles: [], PUT /api/productos/:id/formula responde HTTP 200 y React muestra alerta "Formula guardada".

Regresión Exitosa DEF-01 — F1-CP-03

Ingresar "aloe vera " (minúsculas + espacio) ahora es rechazado con HTTP 409 gracias al índice LOWER(TRIM(nombre)) en PostgreSQL.

Observación HTTP 500 en negativos — F1-CP-06

El stock -1 es rechazado por el CHECK de PostgreSQL (protege datos), pero sin validación previa en React/Express devuelve HTTP 500 en vez de 400.

8. Desafíos Superados, Demostración y Conclusiones

Cierre de Entrega

Principales Desafíos Técnicos

  • Aislamiento de Estado ($L_9$): Limpieza transaccional automática (resetBaseline) en cada test para cero flakiness.
  • Validación Nativa HTML5: Verificación de checkValidity() en Chrome cuando el input bloquea decimales o ceros antes de llegar a la API.
  • Race Condition en Alertas: Sincronización paralela con Promise.all([waitForResponse, waitForEvent('dialog')]).

Comandos de Demostración en Vivo

# 1. Entrar a la suite automatizada
cd tests-e2e

# 2. Demo visual en Chrome (F3 Producción)
npx playwright test tests/f3-produccion.spec.js --headed

# 3. Suite completa (29 casos) + Reporte HTML
npm test
npm run report
Conclusión Final: La automatización con Playwright ejecutó 29 escenarios E2E en 28.5 s (93.10% éxito), garantizando el 100% de integridad atómica en producción y traslados, y revelando 2 defectos reales ocultos (DEF-02 y DEF-03) antes de pasar a producción.
